# 叙事与文案规范（新增层）

> 本文件只补充「怎么组织论点、证据与表达」；不替换 `report-ppt-skill` 的封面、三基调、纵向翻页 runtime、组件、颜色或字号规范。视觉与实现仍以 `SKILL.md`、`components.md`、`type-and-color.md` 和 `deck-architecture.md` 为准。

## 1. 先写叙事地图，再排页面

动手做页面前，用下表写出最小叙事地图。相邻章节若回答同一个问题，就合并或重新定义；无法写出一句结论的章节通常只是剩余内容的容器。

| 章节 | 要回答的问题 | 一句话结论 | 证据或素材 | 下一章承接 |
|---|---|---|---|---|
| 例如：现状与发现 | 问题主要出现在哪里？ | 三个关键步骤造成了大部分等待与返工 | 任务数据、截图、访谈 | 因此需要确定优先解决的体验目标 |

先明确：受众要作什么决策、核心判断是什么、哪些内容是口头汇报的主线、哪些只用于应对追问。页面数量服从叙事，不服从固定页数；内容多时先合并、拆页或放附录，绝不缩小正文。

## 2. 按任务选择叙事模式

可混用，但每个章节只承担一个主要职责；不要为了套结构而加入不需要的章节。

| 模式 | 适用场景 | 推荐主线 |
|---|---|---|
| 体验优化 | 需要证明体验问题并推动改进 | 问题与目标 → 关键证据 → 发现与原因 → 体验目标/策略 → 方案 → 落地与协作 |
| 评测 / 竞品研究 | 需要比较差异并选择机会方向 | 研究问题 → 范围与方法 → 对比发现 → 跨案例规律 → 启示 → 机会方向 |
| 设计提案 | 问题已被接受，需要评估目标体验 | 背景与成功标准 → 体验原则 → 目标旅程/信息架构 → 关键设计时刻 → 取舍与依赖 → 验证计划 |
| 领导决策摘要 | 时间有限，需要批准方向、优先级、责任或资源 | 待决策事项 → 核心判断 → 最小充分证据 → 建议方向 → 优先级与协作 → 风险/边界 |

## 3. 明确证据、推论与方案

- **证据**：直接观察或测量到的事实；说明必要的范围、样本、时间或来源。
- **推论**：由证据支持、但尚未直接测量的解释；用「表明 / 可能源于 / 因此判断」等措辞。
- **方案**：有待验证的设计响应；用「建议 / 目标体验 / 拟通过」等措辞，不写成已实现的效果。

模糊体感（如“慢、乱、重、不可信”）不能停在标签层。拆成可观察条件：真实耗时、等待是否有反馈、价值何时出现、信息负担、完成状态是否清晰等；实际项目只保留与结论有关的维度。

不要用 UX 文案承诺修复模型、平台或工程能力。UX 策略写用户将能理解、判断、控制、检查或确认什么；路由、编排、诊断、重试与平台能力则写成依赖、支撑机制或边界。

## 4. 让发现与方案可回收

工作时维护下表，不需要原样放到 deck 中。它用来避免“有洞察没回应”或“有方案没依据”。

| 发现 | 证据 | 体验目标 | 设计响应 | 用户收益 | 指标 / 依赖 / 边界 |
|---|---|---|---|---|---|

- 正向检查：每个重要发现都有设计响应、明确边界，或说明暂不处理。
- 反向检查：每个设计点都能回指一个发现、目标或已接受原则。
- 方案页只展示建立可信度所需的关系，不把工作表塞满页面。

## 5. 页面文案句法

### 标题和副标题

- 标题写**发现、判断或设计选择**，不要只写栏目名。
  - 不写「用户研究」；写「文档、调试与环境配置构成三类核心障碍」。
  - 不写「方案介绍」；写「将关键状态前置，缩短首次可用价值的等待感」。
- 副标题只补原因、范围、证据边界或术语说明，不重复标题。
- 背景页只交代语境、目标和约束；结论放到发现、策略或建议页，不抢跑。

### 洞察与证据页

默认结构：**结论标题 → 证据主体（数据、VOC、对比、旅程等）→ 必要的范围/来源 → 下一步启示**。

证据不够时降低断言强度，不用大标题掩盖样本或方法边界。多个证据只保留支撑当前结论的最小充分集合，其余进入附录或备页。

### 方案与设计点页

默认结构：**设计图 / 示意 → 3--4 个体验设计点 → 用户收益、验证方式、依赖或取舍**。

- 体验点描述用户能看到、理解、选择、检查或恢复什么；不要只列内部功能名。
- 设计图是方案页的主要证据，标注聚焦 3--4 个点，超过时拆页。
- Before / After 必须使用可比任务、输入和环境；设计解释放在产品画面外，不伪装成真实运行输出。

#### 可选增强：体验设计推导（仅本类页面启用）

当需要解释“为什么这样设计”、从截图/设计稿提炼设计亮点，或验证方案是否回应问题时，才使用本节；不适用于纯数据、竞品、roadmap、封面或一般背景页，也不要求每页都展示完整推导链。

1. 用最短链路梳理：**问题 → 期望用户状态 → 体验策略 → 具体设计点 → 用户收益 → 验证信号或依赖**。
2. 策略保持 3--5 条，彼此有区分；多页面方案优先围绕一条主用户旅程组织，不把零散功能名并列成策略。
3. 每个设计点按四项表达：**设计选择 / 对应问题 / 作用机制 / 用户收益**。可用句式：

   > 通过 **[设计选择]**，解决 **[问题]**，借助 **[作用机制]**，让用户能够 **[具体收益]**。

4. 严格区分层级：
   - **体验策略**：用户能理解、判断、控制、检查或确认什么。
   - **具体设计点**：页面、控件、状态、入口或交互选择如何实现策略。
   - **支撑机制**：路由、编排、模型选择、诊断、调度等使体验成立的系统能力，作为依赖或边界说明。
   - **视觉表达**：布局、颜色、动效、插画等表现方式；它们不是策略本身，需说明怎样转化为用户可感知的价值。
5. 从静态截图或设计稿反推时，先写可见结构、标签、控件与状态；未经验证的跳转、动效、数据流或无障碍行为标为假设。不得凭图虚构用户研究、真实行为或指标。

拒绝「布局更清晰」「更有沉浸感」「提升效率」这类没有因果机制的结论；若无真实指标，写具体可感知的收益或待验证假设，不补造数字。

### 语气与术语

保持现有 skill 的要求：书面、简洁、易懂；去掉口语和不常见表达。全篇对阶段、策略、角色、状态和功能使用同一名称；改名后全局检索目录、页脚、总结和附录中的旧词。

## 6. 核心与附录

核心是帮助受众完成决策的口头路径；附录是支撑追问的证据路径。仅当删除一页会导致受众无法理解问题/决策、信任核心判断、区分策略、评估关键方案，或确认优先级和下一步时，才留在核心。

可合并且仍清晰的相互依赖结论应合并；只增加可信度但不影响主决策的详细方法、原始数据、次要比较和备选方案进入附录。附录建议按：方法与范围 → 详细证据 → 扩展发现 → 支撑规则或备选方案组织；如果 Thank You 在附录前，明确提示后面还有支撑材料。

## 7. 交付前的文案检查

- 每章是否回答不同的问题，并自然承接下一章？
- 每页是否只表达一个主结论？标题能否脱离版式独立成立？
- 证据、推论和方案是否没有混写？
- 每个重要发现是否有响应或明确边界？每个设计点是否有来源？
- 方案页是否写清用户收益、验证方式、依赖或取舍中的必要部分？
- 概念命名是否在目录、页脚、总结、附录一致？

> 封面仍按本 skill 的既有三基调和模板制作。本文件不要求“克制封面”，也不限制使用抽象背景、品牌图形或为主题设计的视觉表达。
